# Sharing previews and production deployment

## Social thumbnail

The social image is a 1200 × 630 PNG at `public/social-preview.png`. It combines the approved cartoon avatar with a warm off-white surface, near-black type, muted supporting text, and a restrained blue accent. It identifies Mason Wang, his Business and Computer Science program at UBC, and `masonwang.dev` without adding an aspirational slogan.

The composition is generated by `scripts/generate-social-preview.mjs` with the existing Sharp dependency. The avatar was previously created with the built-in image tool; its edit prompts are documented in `favicon-generation.md`. No fresh image-generation call is needed to change the thumbnail's text, spacing, or colors.

```sh
npm run generate:social-preview
```

Inspect the generated PNG before committing it. Keep essential content away from the edges and readable when reduced to a small card. The PNG is the final output; the script is the editable source.

`app/lib/social-preview.ts` defines the image URL, dimensions, and alt text once. `app/layout.tsx` reuses it for Open Graph and Twitter's large-image card. Bump the query version when the artwork changes so services see a new image URL. Do not add a conflicting `opengraph-image` file without deciding which metadata source should win.

Third-party sites control their own link-preview caches and may retain an earlier card until they re-fetch the page. Changing the image URL helps invalidate the image cache; it cannot force every service to immediately re-scrape old shared messages. The static Itemle and Lane notes documents have their own HTML heads and do not inherit the portfolio card.

## Release workflow

1. Inspect `git status`; preserve unrelated work. Pull/fetch remote changes before composing a release.
2. Update standalone repos if needed, run their tests, then refresh the portfolio snapshots with `node scripts/sync-projects.mjs`.
3. Generate the social image if its avatar, text, or design changed.
4. Run lint and the production build. Check changed routes and interactions, responsive widths, both themes, PDF links, and image loading as relevant.
5. Commit meaningful changes with descriptive messages. Review `git diff --check` and staged paths before committing. Do not manufacture commits or rewrite published history to inflate activity.
6. Confirm the existing Vercel project and account, then deploy when authorized:

   ```sh
   vercel whoami
   vercel project inspect masonwang
   vercel deploy --prod --yes
   ```

7. Require the deployment to reach `READY` and verify the custom domain. Check the actual returned HTML, not only the deployment dashboard. Push the approved commits to GitHub; if pushing first, do not assume a push deployed anything without checking Vercel.
8. Verify that the remote branch SHA matches the intended local commit. Inspect early runtime errors with the installed CLI's current log syntax:

   ```sh
   vercel logs --deployment <deployment-id> --query 'level:error' --since 5m --json
   ```

Vercel's CLI evolves; check `vercel <command> --help` when a flag changes. A manual deploy does not imply that every future GitHub push is connected to automatic deployment.

## Preview verification

Request `/` with a crawler user agent such as `Twitterbot/1.0`, and check `og:image`, its width/height/alt, `twitter:card`, and `twitter:image`. Request the exact image URL, including its version query, and verify HTTP 200, `image/png`, and 1200 × 630 dimensions. Check a retained subpage to confirm it inherits the intended image.

A visual inspection of the asset and a successful metadata/image fetch verify our output. They do not guarantee a particular platform has refreshed an already-cached message.
